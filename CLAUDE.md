# CLAUDE.md — Правила работы для AI-разработчиков

## Роль

Ты — разработчик в автоматизированной системе AUTOGIT. Ты получаешь конкретные задачи и выполняешь их в изолированных ветках. Твоя работа — писать чистый, рабочий код и тесты.

## Обязательный порядок работы

### Перед началом

1. **Прочитай `PROJECT.md`** — это техническая карта проекта: структура, модули, классы, зависимости.
2. **Прочитай `reports/`** — отчёты предыдущих Worker'ов. Если ветка наследуется от другой ветки (не от develop), там будут отчёты о том, что уже сделано. Это критически важно для понимания контекста.
3. **Прочитай описательные файлы (`ARCHITECTURE.md`)** в директориях, с которыми будешь работать. Например, если задача в `src/models/`, прочитай `src/models/ARCHITECTURE.md` если он существует.
4. **НЕ читай все файлы подряд** — только те, которые нужны для твоей задачи.

### Во время работы

5. **Опора на актуальный код** — перед правкой файла обязательно прочитай его текущую версию. Не гадай как выглядит файл.
6. **Правь только то, что нужно** — не добавляй код, рефакторинг или "улучшения", которые не были запрошены.
7. **Не удаляй существующую логику** — удаление или переписывание текущей логики только если это прямо указано в задаче.
8. **Изоляция блоков** — не ориентируйся на код, который может быть создан в других ветках параллельно, если явно не указана зависимость. Если обнаружил неявную зависимость — отметь это в отчёте.
9. **Путь в первой строке** — первая строка каждого файла с кодом — закомментированный путь файла в проекте (например: `// src/utils/helpers.ts`).
10. **Следуй конвенциям проекта** — стиль кода, именование, структура файлов должны соответствовать тому, что уже есть в проекте.

### Тесты — обязательно

11. **Каждая реализуемая функциональность должна быть покрыта тестами.**
12. **Тесты размещаются** в директории `tests/` или рядом с модулем в файле `*.test.*`.
13. **Тесты должны проверять** что конкретная часть, реализуемая в данной задаче, работает корректно.
14. **Новые тесты не должны ломать существующие.**
15. **Перед коммитом** — запусти тесты и убедись что всё проходит. Если тесты падают — исправь код, а не удаляй тесты.

### После работы — обязательный отчёт

16. **Создай файл отчёта** `reports/REPORT-{branch-name}.md` со следующей структурой:

```markdown
# Отчёт: {название задачи}
Ветка: {branch-name}
Дата: {YYYY-MM-DD}

## Что сделано
- Перечисление конкретных изменений

## Изменённые файлы
- `path/to/file.ts` — что именно изменено/добавлено

## Новые зависимости
- (если добавлены новые пакеты/модули)

## Тесты
- Какие тесты написаны
- Результат запуска тестов

## Архитектурные решения
- Почему выбран такой подход (если неочевидно)

## Обнаруженные проблемы
- Неявные зависимости, потенциальные конфликты, технический долг

## Влияние на другие модули
- Какие части проекта могут быть затронуты этими изменениями
```

17. **Обнови `PROJECT.md`** если ты добавил новые модули, классы или изменил структуру проекта.
18. **Обнови `ARCHITECTURE.md`** в директориях, где ты внёс изменения, если эти файлы существуют.

## Коммиты

- Один логический коммит на задачу (допускается несколько если изменения независимы)
- Сообщение коммита на английском: `Add feature X` / `Fix bug in Y` / `Update tests for Z`
- Отчёт коммитится вместе с кодом

## Минимальное чтение файлов

Читай ТОЛЬКО файлы, необходимые для текущей задачи:
- Файлы, которые задача будет менять или создавать
- Файлы, от которых задача напрямую зависит (импорты, базовые классы, интерфейсы)
- `PROJECT.md` (всегда)
- `reports/` (всегда — для контекста предыдущих изменений)
- `ARCHITECTURE.md` в рабочих директориях (если существует)
- **НЕ читай** все файлы проекта подряд
- **НЕ читай** файлы модулей, с которыми задача не связана
